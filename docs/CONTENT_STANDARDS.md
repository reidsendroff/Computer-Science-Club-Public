# Content Standards

## Required lesson anatomy

Every meeting artifact includes prerequisites, an observable objective, setup, a timed plan, a core build, support options, stretch options, a runnable finish, solutions, and an exit ticket. At least 50% of meeting time is hands-on. Direct teaching occurs in blocks of no more than 8–10 minutes.

## Java accuracy

- Start with a small runnable Java program, `main`, and `System.out.println`.
- Distinguish local variables, parameters, instance fields, and static fields.
- Explain that Java has methods; “function” may be mentioned as a general concept, but examples should use Java terminology.
- Teach access modifiers in context. Prefer private fields with public methods.
- Use `static final` for constants. Do not present mutable public fields as ordinary “global variables.”
- Keep examples small, compilable, and consistent with the named Java version; the supported version is `TBD` pending school-device verification.

## Inclusive difficulty

Call choices core, support, and stretch. They are choices for a task, not permanent member categories. Do not publish names, ranks, scores, or individual skill labels. Provide recovery activities and rechecks after every readiness gate.

## Algorithm integrity

State prerequisites for every algorithm. Do not schedule binary search until the Java Foundations Gate is met. Do not schedule graph traversal until members have practiced collections, stack/queue behavior, map/set use, recursion or iterative state, graph representation, and traversal invariants.

## Privacy and logistics

Do not copy resumes, contact information, attendance, academic grades, private feedback, individual progress, or unapproved officer grade levels into the repository. The user-supplied officer names and roles are working public-facing context. Mark dates, rooms, rules, costs, approvals, and competition details `TBD` until verified from official school or organizer sources; record the source and verification date when confirmed.
